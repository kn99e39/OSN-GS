Worklog 59 (docs/worklogs/59_appended_uncertain_gaussian_trainer_activation.md) built `osn_gs/gaussian/torch_uncertain_trainer_activation.py`, the deferred follow-up [[project_safe_uncertain_proposal_atomic_append_integration]] (worklog 58) itself named as future work: bringing atomically-appended uncertain Gaussian rows into a trainable state.

**Mechanism**: `UncertainGaussianAppendAdapter.append()` requires `model.optimizer is None` (unmodified precondition). This module owns the temporary detach (`old_optimizer = model.optimizer; model.optimizer = None`) around the (unaudited) append call, then re-extends `old_optimizer` in place afterward by reusing `TorchGaussianModel._preserve_optimizer_state()` — the SAME grow-in-place helper `append_gaussians_raw`'s ADC clone/split path already relies on (not new code, not re-audited/modified). Existing Adam moments (`exp_avg`/`exp_avg_sq`) for pre-existing rows are preserved bit-for-bit; newly appended rows start at exactly zero. The optimizer object's identity never changes (extended, never replaced/recreated).

**Only `appended` receipts activate**: `rejected`/`duplicate`/`rolled_back` are no-ops that just restore whatever optimizer was active before the call. `activate_appended_rows()` snapshots `old_optimizer.param_groups`/`.state` (shallow copy suffices — `_preserve_optimizer_state` only ever reassigns `group["params"]` and add/removes `state` dict entries, never mutates an existing inner state dict in place) before attempting the extension; any exception restores that snapshot exactly and marks the attempt `appended_inactive` (row stays appended per worklog 58's own already-committed transaction — NOT rolled back, since that would re-audit worklog 58 — but is explicitly flagged not-yet-trainable rather than silently half-registered).

**Visible/uncertain separation reused, not reimplemented**: appended rows already carry `is_uncertain=True` (worklog 58's `append_gaussians_model_only`, unmodified). Existing `torch_density_control.py` (`certain = ~model.is_uncertain` gradient-driven clone/split mask) and `torch_pipeline.py` (canonical visible-NURBS construction call sites, `~model.is_uncertain`) already exclude uncertain rows from every visible-only path — this module verified that via a direct-gradient test (`.grad` exactly zero on excluded rows after `backward()`) rather than adding new masking logic.

**Scope boundary (deliberate)**: `run_one_training_step()` is a minimal renderer-independent forward/backward/optimizer.step harness for verification only — NOT a wire-up into `TorchTrainer`'s real image-rendering loop, CLI, or checkpoint schedule (Master doc's non-scope for that remains in force; only the narrow `TorchGaussianModel.optimizer` extension itself is approved). `run_safe_uncertain_proposals_append_activate_and_train_step()` is the single "raw evidence -> proposal -> append -> activation -> 1 step" production entry point, tested end-to-end on Sphere (0 candidates -> `step_result=None`, no error) since no real/synthetic scene currently reaches a positive Phase G proposal outside the synthetic planar fixture.

**Verified**: planar fixture (same as worklog 57/58) with a model pre-trained on 3 visible rows — activation preserves old Adam state bit-for-bit, new rows start at zero, `model.optimizer` identity unchanged. A subsequent uncertain-only-loss step: `.grad` exactly zero on visible rows, nonzero on new rows (note: visible row VALUES can still drift slightly post-step from pre-existing residual Adam momentum even with zero gradient — expected Adam behavior, not a masking bug; test this via `.grad`, not post-step value equality). Same-batch rerun -> `duplicate` -> `not_activated`, zero additional growth. Injected `_preserve_optimizer_state` failure (scoped to ONLY the post-append activation call, never wrapped around worklog 58's own append call, which also invokes `_preserve_optimizer_state` harmlessly as a no-op when `optimizer is None`) -> full snapshot-restore verified bit-for-bit, `appended_inactive`. Full pytest 751->759.

**How to apply:** any future real trainer-loop wiring must go through `run_safe_uncertain_proposals_append_and_activate()`/`run_safe_uncertain_proposals_append_activate_and_train_step()`, never call `UncertainGaussianAppendAdapter.append()` directly with an active optimizer. If injecting a NEW failure-mode test around `_preserve_optimizer_state`, scope the mock/patch to only the activation call (not the append call) — patching it unconditionally breaks the append transaction's own harmless internal no-op call too (this tripped up the test suite once this round before narrowing the patch scope).
