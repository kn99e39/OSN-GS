**What this thread is.** A distinct, ongoing rebuild of the *visible-surface* Boundary-first constructor (topology → NURBS chart), triggered by the `curved_annulus` misclassification bug documented in `OSN_GS_Urgent_Work_Master.md` §3.1-§3.2. This is NOT the same thread as [[project_boundary_conditioned_occlusion]] (which is about occluded-region charts/uncertain-Gaussian-proposal/append-adapter, Phase A-H, already Gate-approved through the append adapter). This thread lives entirely in an **isolated** codepath — `nurbs_constructor_benchmark/boundary_first_support.py` + `boundary_first_support_runner.py` + `osn_gs/surface/torch_boundary_*` modules — and explicitly must never touch: the default constructor dispatcher (`nurbs_constructor_benchmark/boundary_first.py::construct_boundary_first`), the legacy/default visible constructor, the trainer, the production pipeline, uncertain-Gaussian proposal/append/ownership/checkpoint code, or real multi-hole patch materialization.

**Canonical principle (user-mandated, §3.2 of the master doc):** one common Boundary-first role contract for ALL topologies. Topology (loop count/nesting) is used only for loop interpretation, ownership, orientation, and validation — never as a dispatcher key choosing a different construction methodology. O-grid, observed-anchor fan, and future multi-loop partitioned patch networks are all *materialization forms* of the same contract, not separate code paths. Constructed/materialized must never be conflated with eligible — quality gate defaults to `review_required` until fidelity/crossing/curved-fit gates are in place.

**v6 artifact diagnosis (do not treat v6 as a valid/production result):** `artifacts/boundary_first_support_review_20260727_v6_resolution96/` has three root causes, all now partially addressed: (1) `torch_boundary_support_network.py` did pure linear interpolation between inner/outer boundary correspondence points; (2) `torch_boundary_constrained_surface.py` materialized the support grid as a degree-1 bilinear wedge; (3) `torch_boundary_central_cap.py` generated one degree-1 anchor-fan patch per raster contour cell (~430 patches for `sine`), producing radial-line blowup.

- **2026-07-27 round 2 (worklog 110, own file per the reversed rule below): geometry-semantics correction + crossing gate.** Round 1's "control_grid row == support curve" approach was flagged as conflating *control polygon* (fitting data) with *evaluated curve* (actual geometry) — only true by coincidence for the radial (`degree_v=1`, non-rational) axis, false for any cubic (`degree_u=3`) edge where only the two Bezier endpoints are on-curve. New module `osn_gs/surface/torch_boundary_review_geometry.py` introduces 5 explicit representation kinds (`observed_evidence_points`, `resampled_observed_evidence`, `control_polygon`, `correspondence_chord`, `evaluated_curve`) via a `ReviewGeometryEntity` dataclass, and always evaluates real iso-parametric edges/curves through `surface.evaluate()` (`evaluate_iso_edge`, `evaluate_interior_iso_curve`) rather than reading `control_grid` directly. The observed-anchor fan's pole↔corner 2-point data is now explicitly a `correspondence_chord`, not a claimed support curve; the actual support curve is evaluated at each patch's own interior `u=0.5` iso-curve. `combine_ordered_patch_boundary()` stitches per-patch evaluated edges into one closed reconstructed boundary with deterministic shared-endpoint dedup (including the wraparound closure). New `detect_support_curve_crossings()`/`classify_support_curve_pair()` classify each pair of *actual evaluated* support curves as `valid_shared_pole`/`valid_shared_boundary_endpoint`/`invalid_interior_crossing`/`near_touching_ambiguous`/`no_crossing`/`not_checked`, using an explicit `expected_shared_point` so legitimate pole convergence is never itself flagged. The runner's `gate_pass` now also requires `not has_invalid_crossing`, so `record.state` can no longer be `constructed` when a crossing is found (still never reaches an `eligible` state — none exists yet).
  - **Real discovery, not a false positive:** running this gate over all 15 benchmark scenes found genuine, previously-invisible support-curve overlap in 6 hole-free (observed-anchor-fan) scenes — `plane`, `sine`, `crease`, `triangle`, `elongated_plane`, `close_parallel_sheets`. E.g. for `plane` (600 pts, seed 0, curve_count=8), segments 3 and 7 of 8 nearly coincide away from the shared pole (~0.003–0.018 units apart across their whole interior, vs. ~0.94 local scale) while all other 27 of 28 segment pairs correctly show only the expected shared-pole touch. Root cause is suspected to be the anchor (pole) sitting near the boundary rather than the geometric center, combined with pure-arclength (not angular) boundary resampling around it — **not yet fixed, root-cause repair of anchor selection/resampling is explicitly out of scope for round 2** and flagged as the top item to decide direction on next.
- **2026-07-27 round 3 (worklog 110 append -- explicit user instruction to append THIS round, then start a fresh Worklog 111 once the separate root-cause round below is done): review-payload semantic correction + crossing-gate refinement, done BEFORE any root-cause fix.**
  - **Materialization vs quality state, canonicalized in the runner** (`_component_quality_state`/`_scene_quality_projection` in `boundary_first_support_runner.py`): `materialization_state` (`materialized`/`not_materialized`) and `quality_state` (`unsupported`/`review_required`/`ineligible`; `eligible` is a defined-but-unreached vocabulary value) are now two independent axes, both at component and scene level. A materialized-but-crossing-invalid component is `materialized` + `ineligible` + `quality_reason="invalid_support_crossing"` — never collapsed with `not_materialized`+`unsupported`. The old `record["state"]` (`constructed`/`review_required`/`unsupported`) is kept ONLY as an explicitly-labeled compatibility projection.
  - **Fan seam semantic fix:** the pole↔corner 2-point *correspondence chord* was being reused directly as the seam entity backing `patch_boundaries` — wrong per instruction (never conflate a chord with a seam even when numerically identical). Now a SEPARATE `evaluate_iso_edge(..., "u0", samples=5, ...)` entity (`representation_kind="evaluated_curve"`) is built independently and used for the seam; the chord stays in `support_correspondence_chords` only. Seam payloads now also carry `edge_a`/`edge_b`/`parameter_direction`/`same_orientation`/`shared_endpoint_policy`/`parameter_samples`.
  - **Crossing scope + representative bundle:** `detect_support_curve_crossings()` always returns `scope="representative_support_curve_bundle_crossing"` and `not_checked_categories=["patch_overlap","jacobian_foldover","seam_inconsistency","full_support_family_crossing"]` so the check is never mistaken for a continuous non-intersection proof. The fan case now evaluates a *bundle* of interior iso-curves per patch (configurable `interior_support_curve_fractions`, default `(0.25, 0.5, 0.75)`, CLI `--interior-support-curve-fractions`) instead of just `u=0.5`.
  - **Tolerance decoupled from sampling resolution:** `classify_support_curve_pair`/`detect_support_curve_crossings` now take an explicit `tolerance_scale` (the runner passes `source_boundary_fidelity.local_spacing_median` — real observed-point density — via `_stable_tolerance_scale()`); the old curve-internal-spacing scale (`fallback_curve_bundle_scale`) is now fallback-only, documented as resolution-dependent and never the production choice. Classification also gained `transversal_intersection` vs `overlapping_support_path` (a single-point crossing vs. a sustained parallel/overlapping run — the real `plane` defect is the latter) via a neighbor-based sub-classifier (`_classify_interior_touch`) that conservatively falls back to `near_touching_ambiguous` when there isn't enough resolution to tell them apart. Confirmed resolution-invariant (8/16/32/64 samples, same classification) in a new test.
  - **Re-swept all 15 scenes with the corrected tolerance+bundle.** Result: 4 of the original 6 flagged scenes (`plane`, `sine`, `triangle`, `close_parallel_sheets`) NO LONGER show `invalid_crossing` — the original "invalid" call was itself partly an artifact of deriving tolerance from curve-sampling spacing rather than true observed-point density (same absolute distance, e.g. `plane`'s patch-3/7 gap, now correctly reads as `near_touching_ambiguous` against the real point-density scale). - **2026-07-27 round 4 (Worklog 112, own NEW file per the explicit user instruction "root-cause 완료되면 새 worklog 사용"): root-cause fix for the anchor-fan crossing defect.** Per-scene attribution (all 6 originally-flagged scenes) found the SAME seam index pair (patch 3 vs patch 7 of 8) at fault in every case — not a coincidence. The raw ordered observed boundary IS star-shaped w.r.t. the chosen anchor at full resolution (>97% angularly monotonic in most cases). The actual bug: `build_boundary_central_cap`'s `_resample_closed()` (in `torch_boundary_central_cap.py`) resampled the boundary into `segment_count` fan corners by PURE ARCLENGTH, which for an off-center anchor or elongated shape distributes corners wildly unevenly in ANGLE around the anchor (e.g. `elongated_plane`: 7 of 8 corners crammed into a ~55° wedge, 1 corner covering the remaining ~305° alone) — the under-constrained "wraparound" segment's Catmull-Rom-style tangent then curves back and overlaps the opposite segment.
  - **Fix:** new `validate_star_shaped_boundary()` computes `monotonicity_ratio = |net angular sweep| / sum(|each step|)` (1.0 = perfectly monotonic) plus a max-single-step-degrees check and a min-total-sweep-degrees check (catches an anchor sitting outside the loop entirely, net sweep ~0). Empirically calibrated: known-concave `u_shape` measures ~0.64, a synthetic anchor-outside-loop fixture measures 0.0, all 6 originally-broken (but genuinely star-shaped) scenes measure 0.85-1.0 — so `min_monotonicity_ratio=0.85` cleanly separates them. If valid, NEW `_resample_closed_by_angle()` resamples by EQUAL ANGLE (same arclength-parameter interpolation pattern as before, substituting angular step for Euclidean length) instead of arclength; if invalid, `build_boundary_central_cap` returns `('unsupported', 'insufficient_observed_interior_support', (), {...})` — no synthetic/fallback anchor, no naive angle-sort without validation. Old arclength-only `_resample_closed()` was deleted (fully superseded, zero remaining callers).
  - **Real pre-existing bug found and fixed as a side effect:** `_materialize_boundary_role_network` in `torch_boundary_first_visible_builder.py` was unconditionally wrapping `build_boundary_central_cap()`'s result as `state="constructed"` regardless of the cap's own `.state` — dormant because the cap previously had no real failure path, but immediately crashed (`ValueError` in `combine_ordered_patch_boundary`) the moment `insufficient_observed_interior_support` became reachable. Fixed to check `cap.state` and propagate `cap.reason` as `unsupported` when the cap itself failed.
  - **Result confirmed by full re-sweep:** all 6 originally-flagged scenes (`plane`, `sine`, `crease`, `triangle`, `elongated_plane`, `close_parallel_sheets`) now show ZERO invalid crossings (every pair is `valid_shared_pole`) — not just downgraded to ambiguous, fully resolved. `u_shape` still correctly rejected (concave, via the earlier/separate anchor-ray-coverage gate, unaffected). One new marginal case surfaced by the same gate: `sine` at `(count=400, seed=2)` and `(600, seed=2)` measures `monotonicity_ratio` ~0.79-0.82 (below 0.85) — a pre-existing test (`test_boundary_first_support_pipeline.py`'s resolution sweep, previously expecting ALL sine/seed/count combos "constructed") was updated to expect exactly these two combos as `insufficient_observed_interior_support`, documented as a genuine new finding (comfortable margin above u_shape's 0.64), not a relaxed regression.

This satisfies "no synthetic anchor, explicit review reason on failure" but not the full "evaluate multiple candidates" design — flagged as remaining work, not claimed as done.
