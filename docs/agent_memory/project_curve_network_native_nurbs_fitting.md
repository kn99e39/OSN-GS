Worklog 97 tests whether fitting NURBS directly from Worklog 96's curve-network structure (instead of discarding it and re-parameterizing via PCA point-cloud UV) produces safer, better-supported surfaces. NURBS degree (2), control grid (6x6), and every Worklog 95/96 piece (latent-surface support, seed curves, tracing, continuous-support validation, curve-family/block construction) are fixed and unmodified.

New modules:
- `osn_gs/surface/torch_curve_network_uv_parameterization.py`: derives `(u, v)` entirely from the curve network, never PCA. `u` per transversal trace (family V) = cumulative chord-length position of its own seed sample along the seed curve, normalized [0,1], fixed for every point on that trace (`C_i(v) ~= S(u_i, v)`). `v` per depth (family U / rungs, `D_j(u) ~= S(u, v_j)`) = the mean, across every trace reaching that depth (only within the block's shared correspondence-depth range, guaranteeing monotonicity by construction), of each trace's own chord-length fraction at that depth -- this reconciles the two families onto one consistent parametric domain. Rung interior points get `u` linearly interpolated by chord-length position along the rung. Fails closed on: degenerate seed chord length, non-monotonic/duplicate u ordering, degenerate u/v extent, insufficient shared correspondence depth, duplicated (u,v) with incompatible 3D geometry, and (discovered during this batch's real-data replay) **inconsistent transversal-curve direction** -- two ADJACENT transversal traces (the only pairs Worklog 96 ever rungs together) walking in broadly opposing directions (cosine similarity <= 0). This last check exposed a real property of Worklog 96's own curve construction (its per-seed-sample inward-hint direction selection is not guaranteed consistent trace-to-trace) without modifying Worklog 96 itself.
- `osn_gs/surface/torch_nurbs.py::fit_torch_visible_surface_from_uv` (new public function): fits at externally-supplied, fixed UV -- IDW seeding via the existing `fit_torch_visible_surface(..., initial_uv=uv)` plus a single regularized LSQ solve via the existing `_solve_control_grid_lsq`, never calling `project_torch_points_to_nurbs` foot-point re-projection, so UV is never re-estimated from 3D geometry mid-fit.
- `osn_gs/surface/torch_curve_network_native_fit.py`: `fit_curve_network_native(block)` (path B) vs `fit_pca_uv(block)` (path A, the unchanged existing `fit_torch_visible_surface_lsq`), no fallback between them (AST-verified: `fit_curve_network_native` never calls the PCA fit function).

Real 7-region paired replay (baseline_compatible checkpoints 2900 and final, same as Worklogs 95/96): at 2900, 7/7 attempted blocks (100%) failed parameterization with `inconsistent_transversal_curve_direction`; at final, 4/5 (80%) failed the same way. **11/12 blocks (91.7%) combined cannot define a valid intrinsic (u,v) domain at all**, despite already satisfying Worklog 96's own 2x2 correspondence contract. The one block that did produce a valid parameterization (final checkpoint) classified as extrapolative, not valid_supported. **Curve-network-native fitting reached zero valid_supported patches at either checkpoint; the paired PCA_UV path retained nonzero valid_supported at both** (2900: 3.41%, final: 13.96%). A synthetic fixture with genuinely consistent transversal-curve direction confirmed the native fitting code itself works correctly (mean residual <0.2) -- the failure is attributable to Worklog 96's curve-family structure, not a fitting-implementation defect.

Decision C: CURVE_NETWORK_PARAMETERIZATION_INVALID. Do not hide this via PCA fallback (not done). Do not tune curve-seed heuristics or run another PCA/UV variant ablation based on this result. See [[project_latent_surface_curve_network_constructor_completion]] for the Worklog 96 block/contract this extends.
