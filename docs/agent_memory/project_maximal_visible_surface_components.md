Worklog 102 (2026-08-21, `arch/2dgs-coverage-first-surface`): the user directed a full philosophy reversal from WL97-101's "conservative regions, prove bilateral smoothness before merging" to **Maximal Visible Connectivity**: start from full observed-visible surfel evidence with connectivity as the DEFAULT, and CUT a local candidate edge only when explicit observation/occlusion/discontinuity evidence requires it. Central distinction: `Physical Surface Continuity != Visible Surface Connectivity` -- two visible surfaces separated by a positive occluded domain stay separate visible components even if they belong to the same underlying physical surface (that's future Occluded Surface construction's job, not this stage's).

New module `osn_gs/surface/torch_maximal_visible_connectivity.py`. Reuses the canonical Phase-C `torch_observation_evidence.py` STATUS constants/dataclasses (`ObservationEvidence`, `CameraViewEvidence`) UNCHANGED -- that module itself is not modified. `classify_world_samples` is a pure-Python per-sample loop built for Phase E's low-hundreds-of-candidates scale, not millions of edges, so a NEW vectorized `_per_view_status_codes` was written and verified BIT-IDENTICAL to `classify_world_samples`'s own output on the same inputs (test: `test_vectorized_per_view_classification_matches_canonical_classify_world_samples`).

**Real bug found and fixed while writing the module docstring, before running any fixture**: the first design ("linearly interpolate the two edge endpoints' own depths as an expected value, compare the camera's screen-space depth against it") is structurally the SAME as the forbidden straight-3D-chord test directive section 5 explicitly warns against (a straight 3D line's camera-space depth is itself approximately linear in the interpolation fraction). Fixed by replacing the point-estimate comparison with a RANGE test: `[min(depth_i,depth_j) - edge_length - depth_epsilon, max(depth_i,depth_j) + edge_length + depth_epsilon]` where `edge_length` is the edge's own 3D Euclidean length (already available, not new) -- a geometrically NECESSARY bound (the true surface between two points at that 3D distance apart cannot have a camera-space depth outside this range, however curved), verified via `test_curved_surface_with_camera_does_not_falsely_trigger_occlusion_from_curvature`.

Also found and fixed a REAL sign bug in the positional-offset formula shared by WL98/99/100 (`tangential_offset` subtracts `normal_offset.unsqueeze(-1) * average_normal` using the ABS value of the signed dot product, which DOUBLES the normal component instead of cancelling it when the signed projection is negative -- masked in all of WL98/99/100's own fixtures by their normals/offsets happening to align sign-positive). Fixed ONLY in this module's own copy (WL100 preserved unmodified per directive); flagged for future correction if WL98/99/100 are ever touched again.

Cut reasons: `CUT_KNOWN_FREE_SPACE`, `CUT_OCCLUDED_DOMAIN` (both new, observation-based), `CUT_VISIBLE_GEOMETRIC_DISCONTINUITY`, `CUT_POSITIONAL_SHEET_SEPARATION` (both WL98's own logic reused VERBATIM -- but as CUT evidence, never as a merge-proof requirement; `interface_smooth_majority_fraction` does not exist in this module at all), `UNRESOLVED_OBSERVATION_CONFLICT` (fail-safe cut when one co-observing camera shows a gap and another shows clean continuity for the same edge).

8 synthetic fixtures required by the directive all pass (14 new tests): flat/curved fully-visible surface (1 component each), wall+occluder+wall (2 components, positive `CUT_OCCLUDED_DOMAIN`), same curved surface with an occluded gap (stays 2 components), known free-space gap (2 components, positive `CUT_KNOWN_FREE_SPACE`), parallel sheets (stay separate), a true sharp discontinuity (preserved), an unobserved gap with NO positive occlusion/free-space evidence (must NOT force a cut -- confirmed). The CPU fallback renderer's own documented limitation ("no real depth-ordered occlusion") made the occluder/free-space fixtures unreliable via normal Gaussian rendering, so those were built with a `_procedural_evidence` helper that fills the SAME `ObservationEvidence`/`CameraViewEvidence` dataclasses with an exact, deterministic z-buffer (not a new system) -- two real pixel-rounding/inset boundary bugs found and fixed while building it.

**Real-scene measurement: clearly negative.** Same checkpoint as WL96-101 (1,190,469 surfels), all 161 train cameras, depth rendered directly via the 2DGS surfel rasterizer. Largest visible component = **92.69%** (13,585 components total) -- worse than WL96's 74.70%, near WL98's 94.51%, far worse than WL100's 22.91%. Of 1,505,170 total cut edges, only 3,065 (1.4%) came from observation-based cuts (occlusion/free-space) -- genuine occluders/free-space gaps between LOCAL candidate-graph neighbors (already gated to within 2x local spacing) are rare at that fine scale. The WL98-reused geometric cuts fired broadly (29.3% of all 5,132,180 spatial edges, `CUT_VISIBLE_GEOMETRIC_DISCONTINUITY`=364,010 exactly matching WL98's own real-scene number -- confirms exact reuse) but STILL were not enough to break percolation in the dense kNN graph, reproducing WL98's own core finding (per-edge local cuts, however individually correct, don't guarantee topological disconnection) in a completely different (connectivity-by-default, not merge-by-proof) architecture. Confirmed directly: WL100's own patio-side and hedge-side seed surfels (node 117922, node 711179) landed in the IDENTICAL final component (same `f_dc` color) -- the percolation WL99/100 fixed reopened here. The table's independence (kept by WL97-100) also disappeared into the giant component.

Full regression 1184 passed, 1 skipped (+14 from WL101's 1170). **No architecture success claimed** -- the observation-state reuse and curvature-safe design work correctly, but real-scene evidence density (especially local-scale occlusion/free-space sparsity) is insufficient to prevent percolation under this philosophy.
