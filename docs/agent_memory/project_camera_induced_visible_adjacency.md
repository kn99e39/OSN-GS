Worklog 107 (2026-08-21, `arch/2dgs-coverage-first-surface`): the user accepted WL106 as a valid negative experiment falsifying "3D candidate edge -> camera approves/contradicts pair -> aggregate" and directed a full inversion: the camera's own rendered visible surface GENERATES local surfel adjacency directly (image-space structure), the existing 3D candidate graph becomes a pure locality-sanity restriction (never independently generates topology), and global topology is the UNION of every view's own positive relations -- a view that cannot observe a relation (occluded, out of frame) contributes no edge but never vetoes another view's positive observation of the same pair. There is structurally no "conflict" state in this architecture at all.

**Renderer investigation (directive section 2):** read `osn_gs/render/vendor/diff_surfel_rasterization/cuda_rasterizer/forward.cu`'s `renderCUDA` directly -- confirmed the kernel already computes `median_contributor` (the per-tile contributor position at the exact point running transmittance T crosses 0.5, forward.cu:407-411) and stores it via `n_contrib[pix_id+H*W]`, but neither `median_contributor` nor the `point_list`/`ranges` needed to convert it to a global surfel index are returned to Python (`rasterize_points.cu`'s `RasterizeGaussiansCUDA` tuple confirmed not to include them). Unlike WL105, the backward-gradient trick here only gives an aggregated per-view boolean (not spatial per-pixel identity), which is insufficient for building actual image-lattice adjacency -- so this batch DID require a real diagnostic-only CUDA modification (directive's preferred, previously-avoided path).

**Diagnostic CUDA build:** new sibling package `osn_gs/render/vendor/diff_surfel_rasterization_diag/` (full copy of the canonical vendored package; canonical itself untouched). Exactly one addition threaded through `forward.cu` -> `rasterizer_impl.cu`/`.h` -> `rasterize_points.cu`/`.h` -> `forward.h`: at the same `if (T > 0.5)` point median_contributor is set, also capture `collected_id[j]` (the global surfel index already in a register there -- no `point_list` reconstruction needed) into a new local `median_surfel_id`, written out as one new (H,W) int32 output tensor (`-1` = no crossing). `backward.cu` untouched (no gradients needed for this diagnostic). Built via `scripts/build_surfel_extension_diag.bat` (mirrors the existing `build_surfel_extension.bat` pattern, same vcvars64.bat + pip install --no-build-isolation), installed as a separate pip package `diff_surfel_rasterization_diag` (own module name, no collision with canonical). New Python module `osn_gs/render/torch_surfel_representative_diagnostics.py` calls `_C.rasterize_gaussians` directly under `torch.no_grad()`, bypassing the canonical autograd wrapper entirely (no gradients ever needed).

**Non-interference proven:** `test_diagnostic_rendering_matches_canonical` shows the diagnostic build's `render`/`depth` outputs are byte-identical to the canonical rasterizer's on the same inputs. `test_occluded_surfel_never_becomes_the_representative` (three stacked near-opaque covering surfels + a far one) confirms the far surfel never becomes any pixel's representative -- real occlusion semantics, not approximated.

**New core module** `osn_gs/surface/torch_camera_induced_visible_adjacency.py`: `accumulate_image_space_pairs` (4-connectivity right/down raster-neighbor comparison of the per-view representative-ID map, union across views, no pixel-radius parameter) -> `filter_by_3d_locality` (existing candidate graph as restriction only, reused unmodified `build_candidate_graph`) -> `apply_secondary_geometric_gate` (WL98/102/103/106's shape-operator residual + corrected signed positional-offset formula, reused verbatim, applied once to the union) -> connected components. No corridor/center-depth-range test exists anywhere in this module (directive's Central Intent A). Worklogs 103/104/105/106 all left completely unmodified and separately replayable.

**Visual/quantitative verification against percolation:** sampled actual pixel colors from `CAMERA_INDUCED_VISIBLE_COMPONENTS`: table center RGB (63,82,200) vs two patio-floor samples (154,71,68)/(149,67,68) -- clearly distinct components; three hedge/background samples all differ from each other and from table/patio -- hedge remains fragmented into many small components, not merged into the giant one. This strongly suggests the 36.77% largest component is the patio floor's own legitimate large continuous surface, not indiscriminate percolation across unrelated objects (qualitatively different from WL96-102's problematic 70-92% giant components that mixed table+patio+hedge) -- though this batch does not claim full quantitative proof (e.g. no explicit spatial-clustering confirmation), and does not declare final architecture success per directive's explicit instruction.
