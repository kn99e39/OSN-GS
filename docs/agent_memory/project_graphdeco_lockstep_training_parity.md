Worklog 62 (docs/worklogs/62_graphdeco_lockstep_training_parity.md) resolved the causal chain traced across the whole "graphdeco vs OSN-GS" investigation arc this session ([[project_osn_gs_direction]]'s "no surface loss on visible Gaussians" invariant + the earlier extent-basis hypothesis, which was correctly rejected by the user, + the first-divergence audit that traced the 3k+ collapse to screen-size pruning triggered by excess anisotropy already present by iteration 600).

**Method**: `scripts/devtools/lockstep_parity_harness.py` initializes a real baseline `GaussianModel` from the actual dataset, then TRANSPLANTS its raw xyz/scaling/rotation/opacity/SH tensors directly into an OSN-GS `TorchGaussianModel` via `replace_tensors()` — byte-identical starting state, confirmed via `torch.equal()`. ADC disabled on both sides so population size (and thus Gaussian index alignment) never changes for the whole run. Camera sequence: replicated baseline's own `random.seed(0)` → `Scene.__init__`'s `random.shuffle` → per-iteration pop-based `randint()` selection algorithm exactly, so both sides train on the literal same camera at every step. Each side still calls its own REAL, unmodified render/loss/optimizer code (never reimplemented).

**Root cause found**: at step 1 (before any gradient applied), the RENDERED IMAGE already differed (`image_mean_abs_diff=0.00051`) from byte-identical tensors and the same nominal camera. Traced to two real bugs in `osn_gs/data/colmap_scene.py`:
1. `camera_fovs()` recomputed FoV from the DOWNSCALED render resolution (dividing focal by `downscale`, using rounded post-resize width/height) instead of computing it ONCE from COLMAP's original camera resolution and never touching it again — which is what baseline's own `utils/camera_utils.py::loadCam` does (FoV is a resolution-independent angle; baseline passes `cam_info.FovX/FovY` through unchanged regardless of `--resolution`). Rounding asymmetry between width/height at non-integer downscale factors (e.g. 3.2419x) caused FoVy to drift measurably while FoVx happened to match.
2. `load_image_tensor()` explicitly forced `Image.BILINEAR` for the ground-truth resize; baseline's `PILtoTorch()` passes no `resample` arg at all, so Pillow's own default (`BICUBIC` for RGB) applies. Confirmed via direct pixel comparison: `gt_mean_abs_diff=0.0049` from identical source pixels and identical target resolution.

**Fix**: `camera_fovs()` now always uses `colmap_camera.width`/`.height` (COLMAP's own recorded original resolution) at both call sites (`load_colmap_scene`, `load_colmap_scene_with_eval_split`); `load_image_tensor()`'s two resize call sites switched `BILINEAR` → `BICUBIC`. Surface reconstruction/reliability code untouched (pure data-loader fix).

**Verified**: post-fix, step 1 matches to float32 noise level (loss 0.26439112 vs 0.26439148, grad norms match to 6+ significant figures, `image_mean_abs_diff=0`, `gt_mean_abs_diff=0.0`). Steps 2-10 show small, slowly-growing residual divergence — attributed to `diff_gaussian_rasterization`'s own atomicAdd-based backward-pass non-determinism (both frameworks share the exact same installed CUDA extension) compounding through nonlinear SGD, not a remaining code difference. At step 600 (ADC still off, population-level stats only): anisotropy median baseline=1.581 vs osn_gs=1.588 — closely tracking, a world apart from the pre-fix real-training gap (selected ADC candidates showing anisotropy 27-37 vs baseline's whole-population p99 of 8.6 at the same iteration). Full pytest 772->775 (3 new focused regression tests for `camera_fovs`'s resolution-independence).

**How to apply:** any future COLMAP/dataset loader change must preserve "FoV computed once from original resolution, never touched again" and "match Pillow's actual resize default (BICUBIC for RGB), don't silently pick a different filter" — these are the two invariants this worklog exists to protect. If a future baseline-comparison investigation finds another apparent OSN-GS-vs-baseline structural training divergence, re-run `lockstep_parity_harness.py` first (cheap, ~2 min for 600 steps) before assuming it's an algorithm-level bug — it isolates render/data-loading-level causes from actual ADC/optimizer/loss-formula differences very effectively, as this round demonstrated.
