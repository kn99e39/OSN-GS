Worklog 105 (2026-08-21, `arch/2dgs-coverage-first-surface`): the user accepted WL104's node-level diagnostic but rejected Branch A as premature, since it relied only on Phase-C's point-sample center test vs the weak `radii>0` signal. Directive: instrument the actual 2DGS rasterizer for real per-surfel image-formation contribution, without modifying the canonical training/rendering path.

**Key engineering decision (documented, not silently substituted):** the directive's preferred approach was a diagnostic COPY of the vendored CUDA extension with new atomic per-primitive output buffers threaded through forward.cu/rasterizer_impl.cu/rasterize_points.cu/ext.cpp + a separate build. Investigated the source directly and found a cheaper, EXACT alternative: `osn_gs/render/vendor/diff_surfel_rasterization/cuda_rasterizer/backward.cu` (completely UNMODIFIED, the same kernel every training step already runs) re-derives the identical 5-condition forward acceptance test (`p.z!=0`, `depth>=near_n`, `power<=0`, `alpha=min(0.99,opa*exp(power))>=1/255`, `test_T=T*(1-alpha)>=0.0001`) and, only for accepted contributors, does `atomicAdd(&dL_dcolors[global_id*C+ch], (alpha*T)*dL_dpixel[ch])` (backward.cu:339). Setting diagnostic loss `L=render_unclamped.sum()` makes `dL_dpixel[ch]=1` uniformly, so `dL_dcolors[global_id]` becomes exactly `sum(alpha*T)` over that surfel's accepted pixels -- not an approximation. New module `osn_gs/render/torch_surfel_contribution_diagnostics.py` calls `torch.autograd.grad(loss, (model._features_dc,))` (NOT `.backward()`, so no parameter's `.grad` is ever mutated) and reads channel-0 of the resulting gradient (all 3 RGB channels carry the identical value for a sum-loss, so channel 0 alone avoids a 3x inflation). Zero lines of the vendored kernel, `OSNSurfelRasterizer`, or `TorchGaussianSurfelModel` were changed; `torch_pipeline.py`/`torch_trainer.py` do not import the new module (AST-checked test).

Limitation documented honestly: this trick recovers "contributed YES/NO" and "accumulated compositing weight" per view (both requested minimums), but NOT per-pixel contributing-pixel-count or max-single-pixel-weight -- those require literal per-pixel bookkeeping the kernel's atomicAdd already collapses; recovering them would need the actual CUDA-copy approach, not attempted this batch.

Proven non-interference (directive section 5): `test_canonical_forward_outputs_unchanged_by_diagnostic_call` shows render/depth outputs are byte-identical before, during (interleaved with the diagnostic `autograd.grad` call), and after -- backward never mutates already-computed forward tensors, and a real diagnostic call was empirically shown to leave `.grad` at `None` throughout.

**Real-scene measurement (same checkpoint/cameras as WL96-104):** cross-tab of Phase-C center-positive vs renderer-contributing, all 1,190,469 surfels: center+/contrib+ 455,357; center+/contrib- 21,572; center-/contrib+ **680,527**; center-/contrib- 33,013. Among the 713,540 surfels WL104 called `NEVER_POSITIVELY_OBSERVED_AT_NODE_LEVEL`, **95.37% (680,527) actually contribute** to the official renderer's alpha-compositing -- median 20 contributing views, mean 29.4, up to 161; median accumulated weight 0.99, mean 4.93 (not marginal noise). All of this cohort is, by construction, exactly WL103's singleton set (cross-tab restricted to WL103 singletons gives identical center-/contrib+ and center-/contrib- counts).

**Branch reassessment: CASE B -- WL104's Branch A is overturned.** Phase-C's point-sample center query is confirmed an inadequate primitive-level visibility definition for trained 2DGS surfels (overlapping/blended planar primitives routinely contribute to accepted alpha-compositing without their own center ever matching the composited first-visible depth within epsilon). Per directive: stopped here -- no epsilon tuning, no new contribution threshold, no new adjacency mechanism this batch. The next architecture decision must define visible topology using renderer-grounded surfel evidence (this batch's new `RendererContributionEvidence`), but that choice is explicitly out of scope here.

Visual confirmation: `CENTER_VS_RENDERER_CONTRIBUTION_VIEW` shows the hedge/background area -- solid dark red (`NODE_NEVER_POSITIVELY_VISIBLE`) in WL104's `SINGLETON_CAUSE_VIEW` -- is instead predominantly orange (`CENTER_NEGATIVE_CONTRIBUTING`) here; `RENDERER_CONTRIBUTION_VIEW`'s view-count ramp shows hedge/background carries substantial (not near-zero) contribution mass across many views.
